1//! Composable and generic RISC-V interpreter.
2//!
3//! This interpreter is designed to work with abstractions from [`ab-riscv-primitives`] crate and is
4//! similarly composable with a powerful macro system and trait abstractions over handling of
5//! memory, syscalls, etc.
6//!
7//! [`ab-riscv-primitives`]: ab_riscv_primitives
8//!
9//! The immediate needs dictate the current set of available instructions and extensions. Consider
10//! contributing if you need something not yet available.
11//!
12//! `ab-riscv-act4-runner` crate in the repository contains a complementary RISC-V Architectural
13//! Certification Tests runner for <https://github.com/riscv-non-isa/riscv-arch-test> that ensures
14//! correct implementation.
15//!
16//! Does not require a standard library (`no_std`) or an allocator, never panics, almost 100% of the
17//! API abstractions are usable in const, including several extensions beyond base ISA.
18//!
19//! ## Supported ISA variants and extensions
20//!
21//! ISA variants:
22//! * RV32I (version 2.1)
23//! * RV32E (version 2.0)
24//! * RV64I (version 2.1)
25//! * RV64E (version 2.0)
26//!
27//! Extensions:
28//! * A (version 2.1)
29//! * M (version 2.0)
30//! * B (version 1.0.0)
31//! * Zaamo (version 1.0.0)
32//! * Zabha (version 1.0.0)
33//! * Zacas (version 1.0.0)
34//! * (experimental) Zalasr (version 1.0.0)
35//! * Zalrsc (version 1.0.0)
36//! * Zawrs (version 1.0.0)
37//! * Zba (version 1.0.0)
38//! * Zbb (version 1.0.0)
39//! * Zbc (version 1.0.0)
40//! * Zbkb (version 1.0.1)
41//! * Zbkc (version 1.0.1)
42//! * Zbkx (version 1.0.1)
43//! * Zbs (version 1.0.0)
44//! * Zca (version 1.0.0)
45//! * Zcb (version 1.0.0)
46//! * (experimental) Zcmp (version 1.0.0)
47//! * Zicond (version 2.0)
48//! * Zicsr (version 2.0)
49//! * Zkn (version 1.0.1)
50//! * Zknd (version 1.0.1)
51//! * Zkne (version 1.0.1)
52//! * Zknh (version 1.0.1)
53//! * Zkr (version 1.0.1)
54//! * Zvbb (version 1.0.0)
55//! * Zvbc (version 1.0.0)
56//! * ZveXx (version 1.0.0), where `X` is anything allowed by the specification like Zve32x or
57//!   Zve64x
58//! * Zvkb (version 1.0.0)
59//! * Zvl*b (version 1.0.0), where `*` is anything allowed by the specification like Zvl128b or
60//!   Zvl512b
61//!
62//! All extensions except experimental pass all relevant RISC-V Architectural Certification Tests
63//! (ACTs) using the ACT4 framework.
64//!
65//! Any permutation of compatible extensions is supported.
66//!
67//! Experimental extensions may not have ACT4 tests yet and are not guaranteed to work correctly.
68//!
69//! ## Design choices
70//!
71//! This crate was designed with a blockchain use case in mind, though it is in no way tied to any
72//! particular blockchain and is completely general purpose. As a result, the implementation is
73//! designed to be precise and non-ambiguous.
74//!
75//! A few key points:
76//! * anything "reserved" in the specification is considered to be illegal
77//! * anything "optional" in the specification is considered to be illegal
78//! * anything "implementation-defined" in the specification is selected to be the most natural and
79//!   deterministic
80//! * type system is used to make the majority of invalid invariants impossible to represent in code
81//!   and/or decode
82//!
83//! Examples:
84//! * `vma`/`vta` are always undisturbed in vector extensions
85//! * Zve64x extension instructions are purposefully restricted to what it is required to be capable
86//!   of, although it would be cheaper to support the fuller feature set only required by V
87//!   extension
88//!
89//! ### Instruction implementations are assembled, not compiled in place
90//!
91//! Instruction implementations are not compiled where they are written. `build.rs` calls
92//! `ab_riscv_macros::process_instruction_macros()`, which parses the sources marked with the
93//! `#[instruction]` and `#[instruction_execution]` attribute macros and writes a generated
94//! execution implementation per instruction set into `OUT_DIR`.
95//!
96//! Macros have documentation about how they work, but the important thing is that `match`
97//! expressions are parsed and re-assembled as needed instead of being compiled in place.
98//!
99//! Two things follow from this, and both constrain how instruction implementations must be written:
100//! * the same arm is expanded into more than one crate, so a `crate::`-relative path inside an arm
101//!   resolves against whichever crate it landed in and is avoided. Shared code is reached through
102//!   helper modules re-exported from [`prelude`] - like `rv64_zbb_helpers` and similar - so that an
103//!   arm can name them unqualified wherever it ends up
104//! * because each arm is kept separately and names exactly the operands its instruction uses, the
105//!   same arms can be emitted as something other than one large `match`. Emitting them as
106//!   standalone per-instruction functions, dispatched by tail call, is what allows an interpreter
107//!   to avoid decoding operands that the instruction about to run does not use, and to stop paying
108//!   for extensions that are compiled in but never executed
109

254/// Virtual memory interface
255pub const trait VirtualMemory {
256    /// Read a value from memory at the specified address
257    fn read<T>(&self, address: u64) -> Result<T, VirtualMemoryError>
258    where
259        T: BasicInt;
260
261    /// Unchecked read a value from memory at the specified address.
262    ///
263    /// # Safety
264    /// The address and value must be in-bounds.
265    unsafe fn read_unchecked<T>(&self, address: u64) -> T
266    where
267        T: BasicInt;
268
269    /// Read a contiguous byte slice from memory
270    fn read_slice(&self, address: u64, len: u32) -> Result<&[u8], VirtualMemoryError>;
271
272    /// Read as many contiguous bytes as possible starting at `address`, up to `len` bytes total.
273    ///
274    /// Can return an empty slice in cases like when the address is out of bounds.
275    fn read_slice_up_to(&self, address: u64, len: u32) -> &[u8];
276
277    /// Write a value to memory at the specified address
278    fn write<T>(&mut self, address: u64, value: T) -> Result<(), VirtualMemoryError>
279    where
280        T: BasicInt;
281
282    /// Write a contiguous byte slice to memory
283    fn write_slice(&mut self, address: u64, data: &[u8]) -> Result<(), VirtualMemoryError>;
284}

342/// Generic program counter
343pub const trait ProgramCounter<Address, Memory, CustomError = CustomErrorPlaceholder>
344where
345    Address: Copy,
346{
347    /// Get the current value of the program counter
348    fn get_pc(&self) -> Address;
349
350    /// Get the previous value of the program counter before executing an `instruction`.
351    ///
352    /// This is usually called from under instruction execution when the program counter is already
353    /// advanced during instruction fetching. As such, `pc - instruction_size` is expected to never
354    /// underflow.
355    #[inline(always)]
356    #[cfg_attr(feature = "no-panic", no_panic_const::no_panic(const))]
357    fn old_pc(&self, instruction_size: u8) -> Address
358    where
359        Address: [const] From<u8> + [const] Sub<Output = Address>,
360    {
361        // TODO: Wrapping subtraction would be nice, but causes a lot of additional generic bounds
362        //  that are bad for ergonomics
363        self.get_pc() - Address::from(instruction_size)
364    }
365
366    /// Apply [`ExecutionResult::Branch`], continuing `offset` bytes from the instruction being
367    /// executed.
368    ///
369    /// A simple implementation can resolve the offset against the program counter and call
370    /// [`Self::set_pc()`]. Implementation that keeps the program counter as a position in an
371    /// already decoded instruction stream can move within that stream directly, which avoids
372    /// converting an address back into a position.
373    fn set_pc_relative(
374        &mut self,
375        memory: &Memory,
376        instruction_size: u8,
377        offset: i32,
378    ) -> Result<ControlFlow<()>, ExecutionError<Address, CustomError>>;
379
380    /// Set the current value of the program counter
381    fn set_pc(
382        &mut self,
383        memory: &Memory,
384        pc: Address,
385    ) -> Result<ControlFlow<()>, ExecutionError<Address, CustomError>>;
386}

453/// Execution errors.
454///
455/// The variants of [`VirtualMemoryError`] and [`CsrError`] are inlined
456/// here rather than nested. Nesting cost an extra discriminant per level, which made this type 24
457/// bytes; flattened it is 16, which is what lets `Result<_, ExecutionError>` be returned in
458/// registers instead of through a hidden out-pointer. `From` implementations for all three are
459/// provided, so `?` on them keeps working unchanged.
460///
461/// Note that a large `CustomError` will grow this type past that threshold again.
462#[derive(Debug, thiserror::Error)]
463pub enum ExecutionError<Address, CustomError = CustomErrorPlaceholder>
464where
465    Address: Copy,
466{
467    /// Unaligned instruction
468    #[error("Unaligned instruction at address {address}")]
469    UnalignedInstruction {
470        /// Address of the unaligned instruction fetch
471        address: PackedAddress<Address>,
472    },
473    /// Out-of-bounds read
474    #[error("Out-of-bounds read at address {address}")]
475    OutOfBoundsRead {
476        /// Address of the out-of-bounds read
477        address: PackedAddress<u64>,
478    },
479    /// Out-of-bounds write
480    #[error("Out-of-bounds write at address {address}")]
481    OutOfBoundsWrite {
482        /// Address of the out-of-bounds write
483        address: PackedAddress<u64>,
484    },
485    /// Unsupported `ecall` instruction
486    #[error("Unsupported `ecall` instruction at address {address:#x}")]
487    EcallUnsupported {
488        /// Address of the unsupported instruction
489        address: PackedAddress<Address>,
490    },
491    /// Unimplemented/illegal instruction
492    #[error("Unimplemented/illegal instruction at address {address:#x}")]
493    IllegalInstruction {
494        /// Address of the `unimp` instruction
495        address: PackedAddress<Address>,
496    },
497    /// Read only CSR
498    #[error("Read only CSR {csr_index:#x}")]
499    CsrReadOnly {
500        /// Index of CSR where write was attempted
501        csr_index: u16,
502    },
503    /// Illegal read access
504    #[error("Illegal read access to CSR {csr_index:#x}")]
505    CsrIllegalRead {
506        /// Index of the accessed CSR
507        csr_index: u16,
508    },
509    /// Illegal write access
510    #[error("Illegal write access to CSR {csr_index:#x}")]
511    CsrIllegalWrite {
512        /// Index of the accessed CSR
513        csr_index: u16,
514    },
515    /// Unknown CSR
516    #[error("Unknown CSR {csr_index:#x}")]
517    CsrUnknown {
518        /// Index of the accessed CSR
519        csr_index: u16,
520    },
521    /// Insufficient privilege level
522    #[error(
523        "Insufficient privilege level for CSR {csr_index:#x}: required {required:?}, \
524        current {current:?}"
525    )]
526    CsrInsufficientPrivilege {
527        /// Index of the accessed CSR
528        csr_index: u16,
529        /// Required privilege level
530        required: PrivilegeLevel,
531        /// Current privilege level
532        current: PrivilegeLevel,
533    },
534    /// Custom error
535    #[error("Custom error: {0}")]
536    Custom(CustomError),
537}

539/// Where execution continues after an instruction, or why it could not.
540///
541/// Instructions describe control flow rather than performing it: they say where execution goes next
542/// instead of moving the program counter themselves. This keeps instruction bodies independent of
543/// how the program counter is represented, which is what allows the same bodies to drive both an
544/// interpreter loop that owns a program counter and one that carries it in a register.
545#[derive(Debug)]
546pub enum ExecutionResult<Reg, CustomError = CustomErrorPlaceholder>
547where
548    Reg: Register,
549{
550    /// Write the register and continue with the instruction that follows this one
551    Continue {
552        /// Register to write
553        rd: Reg,
554        /// Value to write into it
555        value: Reg::Type,
556    },
557    /// Continue with the instruction that follows this one without writing to `rd` register
558    ContinueNoWrite,
559    /// Continue `offset` bytes away from the address of *this* instruction.
560    ///
561    /// Keeping it relative rather than resolving it against the program counter here means a
562    /// pre-decoded interpreter can reach the target by moving within the decoded stream instead of
563    /// converting an address back into a position.
564    Branch {
565        /// Signed byte offset from this instruction
566        offset: i32,
567    },
568    /// Continue at an absolute guest address, as `jalr`-style jumps produce
569    Jump {
570        /// Address to continue at
571        target: Reg::Type,
572    },
573    /// Stop execution
574    Break,
575    /// Execution failed
576    Err(ExecutionError<Reg::Type, CustomError>),
577}
578
579const {
580    // Ensure result type retains its size
581    assert!(size_of::<ExecutionResult<Reg<u64>>>() <= 16);
582    assert!(size_of::<ExecutionResult<Reg<u32>>>() <= 16);
583}

722/// CSR error
723#[derive(Debug, thiserror::Error)]
724pub enum CsrError<CustomError = CustomErrorPlaceholder> {
725    /// Read only CSR
726    #[error("Read only CSR {csr_index:#x}")]
727    ReadOnly {
728        /// Index of CSR where write was attempted
729        csr_index: u16,
730    },
731    /// Illegal read access

733    IllegalRead {
734        /// Index of the accessed CSR
735        csr_index: u16,
736    },
737    /// Illegal write access
738    #[error("Illegal write access to CSR {csr_index:#x}")]
739    IllegalWrite {
740        /// Index of the accessed CSR
741        csr_index: u16,
742    },
743    /// Unknown CSR
744    #[error("Unknown CSR {csr_index:#x}")]
745    Unknown {
746        /// Index of the accessed CSR
747        csr_index: u16,
748    },
749    /// Insufficient privilege level
750    #[error(
751        "Insufficient privilege level for CSR {csr_index:#x}: required {required:?}, \
752        current {current:?}"
753    )]
754    InsufficientPrivilege {
755        /// Index of the accessed CSR
756        csr_index: u16,
757        /// Required privilege level
758        required: PrivilegeLevel,
759        /// Current privilege level
760        current: PrivilegeLevel,
761    },
762    /// Custom error
763    #[error("Custom error: {0}")]

928pub const trait ExecutableInstructionCsr<ExtState, CustomError = CustomErrorPlaceholder>
929where
930    Self: Instruction,
931{
932    /// Prepare CSR read.
933    ///
934    /// This method is called on each extension one by one with the `raw_value` (contents of the
935    /// corresponding CSR register) and initially zero-initialized `output_value`. In return value
936    /// every extension can accept (`Ok(true)`), ignore (`Ok(false)`) or reject (`Err(CsrError)`)
937    /// read request. For accepted reads the extension must update `output_value` accordingly, which
938    /// will be the value used by the `Zicsr` extension handler.
939    ///
940    /// Some extensions will just copy `raw_value` to output value, others will copy only some bits
941    /// or zero some bits of the `raw_value`, as required by the specification.
942    ///
943    /// `will_write` indicates whether the CSR instruction performing this read will also perform a
944    /// write immediately afterward (as part of the same instruction). It is always `true` for
945    /// `csrrw{,i}`, and `true` for `csrrs{,i}`/`csrrc{,i}` unless their `rs1`/`zimm` operand is
946    /// zero (in which case they are a pure read with no write). Some CSRs (e.g. `Zkr`'s `seed`)
947    /// are only legal to access through a genuine read-write instruction and must reject the read
948    /// when `will_write` is `false`.
949    ///
950    /// If no extension returns `Ok(true)`, the read operation is implicitly rejected as illegal
951    /// access.
952    #[inline(always)]
953    fn prepare_csr_read(
954        ext_state: &ExtState,
955        csr_index: u16,
956        will_write: bool,
957        raw_value: RegisterType<Self>,
958        output_value: &mut RegisterType<Self>,
959    ) -> Result<bool, CsrError<CustomError>> {
960        // These are for cleaner trait API without leading `_` on arguments
961        let _: &ExtState = ext_state;
962        let _: u16 = csr_index;
963        let _: bool = will_write;
964        let _: RegisterType<Self> = raw_value;
965        let _: &mut RegisterType<Self> = output_value;
966        // The default implementation is to not allow anything
967        Ok(false)
968    }
969
970    /// Prepare CSR write.
971    ///
972    /// This method is called on each extension one by one with `write_value` being prepared by the
973    /// `Zicsr` extension handler. In return value every extension can accept (`Ok(true)`), ignore
974    /// (`Ok(false)`) or reject (`Err(CsrError)`) write request. For accepted writes the extension
975    /// must update `output_value` accordingly, which will be written to the corresponding CSR
976    /// register.
977    ///
978    /// Some extensions will just copy `write_value` to output value, others will copy some bits or
979    /// zero some bits of the `write_value`, as required by the specification.
980    ///
981    /// If no extension returns `Ok(true)`, the write operation is implicitly rejected as illegal
982    /// access.
983    #[inline(always)]
984    fn prepare_csr_write(
985        ext_state: &mut ExtState,
986        csr_index: u16,
987        write_value: RegisterType<Self>,
988        output_value: &mut RegisterType<Self>,
989    ) -> Result<bool, CsrError<CustomError>> {
990        // These are for cleaner trait API without leading `_` on arguments
991        let _: &mut ExtState = ext_state;
992        let _: u16 = csr_index;
993        let _: RegisterType<Self> = write_value;
994        let _: &mut RegisterType<Self> = output_value;
995        // The default implementation is to not allow anything
996        Ok(false)
997    }
998}

1000/// Trait for executable instructions
1001pub const trait ExecutableInstruction<
1002    Regs,
1003    ExtState,
1004    Memory,
1005    PC,
1006    InstructionHandler,
1007    CustomError = CustomErrorPlaceholder,
1008> where
1009    Self: ExecutableInstructionOperands + ExecutableInstructionCsr<ExtState, CustomError>,
1010{
1011    /// Execute instruction.
1012    ///
1013    /// Instructions might place additional constraints on `ExtState` to require additional
1014    /// registers or other resources. If no such constraint is used, `()` can be used as a
1015    /// placeholder.
1016    ///
1017    /// On success `ExecutionResult::Continue { rd: rd, value: rd_value }` is returned, which will
1018    /// be written into the register file. In most cases this is the only register that needs to
1019    /// be written. If no value needs to be written, `ExecutionResult::ContinueNoWrite` should be
1020    /// returned, which skips the register file write entirely.
1021    fn execute(
1022        self,
1023        rs1rs2_values: Rs1Rs2OperandValues<<Self::Reg as Register>::Type>,
1024        regs: &mut Regs,
1025        ext_state: &mut ExtState,
1026        memory: &mut Memory,
1027        program_counter: &mut PC,
1028        system_instruction_handler: &mut InstructionHandler,
1029    ) -> ExecutionResult<Self::Reg, CustomError>;
1030}

1032/// Outcome of [`ThreadedExecutableInstruction::execute_threaded()`].
1033///
1034/// Unlike [`ExecutionResult`], this is produced exactly once, by the handler that stops the chain
1035/// and is not on the per-instruction path.
1036///
1037/// The instruction fetcher travels through the chain by value and comes back here to remain
1038/// available, exactly as it would be after [`ExecutableInstruction::execute()`].
1039#[derive(Debug)]
1040pub struct ThreadedExecutionResult<IF, I, CustomError = CustomErrorPlaceholder>
1041where
1042    I: Instruction,
1043{
1044    /// Instruction fetcher as of the moment execution stopped
1045    pub instruction_fetcher: IF,
1046    /// Why execution stopped
1047    pub outcome: Result<(), ExecutionError<Address<I>, CustomError>>,
1048}
1049
1050impl<IF, I, CustomError> ThreadedExecutionResult<IF, I, CustomError>
1051where
1052    I: Instruction,
1053{
1054    /// Execution stopped gracefully
1055    #[inline(always)]
1056    pub const fn stopped(instruction_fetcher: IF) -> Self {
1057        Self {
1058            instruction_fetcher,
1059            outcome: Ok(()),
1060        }
1061    }
1062
1063    /// Execution failed
1064    #[inline(always)]
1065    pub const fn failed(
1066        instruction_fetcher: IF,
1067        error: ExecutionError<Address<I>, CustomError>,
1068    ) -> Self {
1069        cold_path();
1070        Self {
1071            instruction_fetcher,
1072            outcome: Err(error),
1073        }
1074    }
1075}

1077/// Tail-call-threaded counterpart of [`ExecutableInstruction`].
1078///
1079/// [`ExecutableInstruction::execute()`] describes what a single instruction does and leaves both
1080/// fetching and control flow to a driver loop. This trait instead runs the whole program: it is
1081/// generated as one handler function per instruction variant, each of which executes its own
1082/// instruction and then tail-calls (`become`) the handler of the next one, so there is no loop and
1083/// no return until execution stops. Each handler touches only the operands its own instruction
1084/// names, which is what the shared loop cannot do.
1085///
1086/// Instruction implementations are unaffected: the handlers are assembled from the very same
1087/// `match` arms that [`ExecutableInstruction::execute()`] are assembled from, so both paths execute
1088/// identical logic and a caller picks between them purely on the trade between code size
1089/// (`execute`) and throughput (`execute_threaded`).
1090///
1091/// This trait is deliberately not `const`, unlike [`ExecutableInstruction`]: dispatch goes through
1092/// a table of function pointers, and calls through a function pointer are not allowed in
1093/// `const fn`.
1094pub trait ThreadedExecutableInstruction<
1095    Regs,
1096    ExtState,
1097    Memory,
1098    PC,
1099    InstructionHandler,
1100    CustomError = CustomErrorPlaceholder,
1101> where
1102    Self: ExecutableInstruction<Regs, ExtState, Memory, PC, InstructionHandler, CustomError>,
1103    PC: InstructionFetcher<Self, Memory, CustomError>,
1104{
1105    /// Execute instructions starting at the instruction fetcher's current position and continue
1106    /// until execution stops or fails.
1107    ///
1108    /// The instruction fetcher is taken by value rather than behind a reference so that it stays in
1109    /// registers across the whole handler chain and is returned in [`ThreadedExecutionResult`].
1110    ///
1111    /// `ext_state` and `system_instruction_handler` are taken by value for the same reason and one
1112    /// more: an owned value can be a zero-sized type, which occupies no argument register at all,
1113    /// whereas a `&mut` occupies one whether there is anything behind it or not. Most
1114    /// configurations have no extension state and a stateless system instruction handler, so both
1115    /// vanish, allowing more registers for other arguments. A configuration that does have a state
1116    /// passes a `&mut` to it (which is an owned value too and for which there are blanket
1117    /// implementations for convenience).
1118    fn execute_threaded(
1119        instruction_fetcher: PC,
1120        regs: &mut Regs,
1121        ext_state: ExtState,
1122        memory: &mut Memory,
1123        system_instruction_handler: InstructionHandler,
1124    ) -> ThreadedExecutionResult<PC, Self, CustomError>;
1125}
